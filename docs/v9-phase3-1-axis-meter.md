## 3. メーターの新しい表示方法

### 変更前

```
🪫 LOW                    🔋 HIGH
████████████░░░░░░░░░░░░░░░░░░░░       ← 左→右に塗るだけ。軸名も位置も無い
```

### 変更後

```
エネルギー                   ややLOW寄り      ← 軸名（左） / 位置（右・タイプカラー）
🪫 LOW  ─────●───┼──────────  HIGH 🔋      ← つまみ + 中央目盛り + 中央→つまみの塗り
```

1行あたり2行構成、4軸で**カード高さ322px**（375px幅、実測）。旧実装（4本のバーのみ）から大きくは増えていません。

実装のポイント:

| 要素 | 役割 |
|---|---|
| **つまみ（●）** | 値の位置そのもの。14pxの円。**端でも欠けないよう、つまみの直径分を差し引いた範囲に配置** |
| **中央の目盛り（┼）** | 「どちらでもない」の基準。これがあるので0や100が「端」だと分かる |
| **中央→つまみの塗り** | どちら側にどれだけ寄っているかの「向き」を見せる。**中央が起点なので、0でも塗りが消えない** |
| **位置ラベル** | 「ややLOW寄り」などの日本語。数値の代わり |

位置ラベルは中央からの距離で4段階:

| 中央からの距離 | ラベル |
|---|---|
| 7以下 | まんなか |
| 20以下 | やや◯◯寄り |
| 35以下 | ◯◯寄り |
| それ以上 | かなり◯◯寄り |

`aria-label`（例: 「温度: かなりCOOL寄り」）も付けています。

## 4. 「100%＝満点」に見えないようにした方法

3つを組み合わせました。

**(1) 数値を一切表示しない。** 実測で確認済み（`^\d{1,3}%$` に一致する要素がページ内にゼロ）。旧実装でも数値は出していませんでしたが、**バーが端まで埋まること自体が「MAX」に見えていた**のが問題でした。

**(2) 塗りの起点を左端から中央へ移した。** これが本質的な解決です。左端起点だと塗りの長さ＝量に見えますが、中央起点だと塗りは「中央からどちらへどれだけ離れたか」にしか読めません。

**(3) 注記を1行だけ追加。**

> これは良し悪しの点数ではなく、カラダのクセの方向を表しています。

4本のメーターの下、カード内に1箇所だけ。文章は増やしていません。

**実測での効き方** — 01 充電下手のうるおいは値100ですが、表示は **「かなりWET寄り」** になります。「うるおい100%（満点）」ではなく「うるおいは WET 側に強く寄っている」と読めます。

## 5. 「めぐり不足」と軸名の衝突をどう処理したか

### 「めぐり」は採用しませんでした。採用すると矛盾が画面に出ます

flowメーターは `100 - (ST + STA)/2` で、**ST/STA はストレス系統＝07 カラダ渋滞・08 イライラ充満・11 頭ぐるぐる・14 常時アクセルの軸**です。**10 めぐり不足の軸（BL）は、このメーターに一切入っていません。**

実測値で確認すると:

| タイプ | flowメーターの値 | 「めぐり」と名付けた場合の表示 |
|---|---|---|
| **10 めぐり不足** | **76** | **「めぐり: FLOW寄り」** |

つまり **「めぐり不足」と診断された人が、同じ画面で「めぐり は FLOW 寄り（＝めぐっている）」と表示される**ことになります。名前と真逆です。さらに `resultTypes.ts` 内で「めぐり」は 04 むくみストックの charges（「散歩でめぐりを促す」）にも使われており、3つの別の意味で使い回されることになります。

### 候補の比較

| 候補 | 既存コピーとの衝突 | 判定 |
|---|---|---|
| **めぐり** | **10のタイプ名**＋04のcharges。しかもこのメーターは10の軸を含まない | ❌ 矛盾が画面に出る |
| めぐり・流れ | 「めぐり」を含むので上と同じ問題 | ❌ |
| カラダの流れ | 衝突なし。ただし他3つが「エネルギー / 温度 / うるおい」と短いので不揃い | △ |
| **流れ** | **衝突なし。むしろ補強になる**（下記） | ✅ **採用** |

### 「流れ」を選んだ理由

`resultTypes.ts` 全体を検索したところ、「流れ」は**1箇所だけ**、**07 カラダ渋滞の catchCopy「流れが止まると調子が落ちる。」**に出てきます。

そして **07 カラダ渋滞こそ、このメーターの STUCK 端そのもの**です（primary = STA、実測で flow = 18 → 「STUCK寄り」）。つまり07の人は、

- キャッチコピー: 「流れが止まると調子が落ちる。」
- メーター: 「流れ … STUCK寄り」

と、**同じ画面で同じことを2回言う**形になります。衝突ではなく補強です。「渋滞 ↔ 流れ」という語の対応も自然です。

### 「うるおい」はそのまま採用しました

09 うるおい不足とはタイプ名が重なりますが、こちらは**メーターと診断結果が一致します**（実測: 09のうるおい = 25 → 「DRY寄り」）。名前が「うるおい不足」で、メーターが「DRY寄り」なので、読んで矛盾しません。「流れ」とは状況が逆です。

**タイプ10の名前「めぐり不足」は変更していません。**

## 補足: 今回の作業で見えたこと（対応不要・記録のみ）

実測表を眺めていて気づいた点を1つだけ記録しておきます。**今回は対応していません。**

**10 めぐり不足の軸（BL）は、うるおいメーターに入っています。** 計算式 `moisture = 100 - (BL + JIN)/2` のためです。実測では BL=100 / JIN=0 なので うるおい = 50 =「まんなか」になり、**めぐり不足の人の4軸は「かなりHIGH寄り / FLOW寄り / COOL寄り / まんなか」で、どこにも「足りていない」が出ません。**

これは凍結対象の計算式の性質なので、今回の表示改善では触れませんでした。対応するとしたら計算式かタイプ名の側の話になるため、判断が必要であれば別フェーズとして扱うのが適切だと思います。
